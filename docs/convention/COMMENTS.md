# 주석 컨벤션

상태: 적용. 작성일: 2026-10-07. 기준: ken-blog `docs/convention/KDoc.md`(2026-10-06 Java 판).

Java API(`apps/api`)에는 Javadoc 규칙을, 그 밖의 언어에는 내용·문체·유지보수 원칙을 적용한다. 코드를 추가하거나 수정할 때마다 이 문서를 따른다.

## 적용 범위

- Java 애플리케이션의 선언 문서는 Javadoc으로 작성한다.
- Java 구현 내부와 Gradle Groovy DSL의 설명에는 일반 주석(`//`)을 사용한다.
- TypeScript·JavaScript·CSS·SQL·YAML·Dockerfile·셸 스크립트에도 아래의 내용·문체·유지보수 원칙을 적용한다. Javadoc 태그와 심볼 링크 문법은 Java에만 적용한다.
- 생성 코드(`apps/api/build/generated-src/jooq` 등), Gradle Wrapper, 외부 라이선스 고지는 직접 수정하지 않는다.
- 이미 적용된 Flyway 마이그레이션 SQL은 체크섬이 바뀌므로 주석을 포함해 수정하지 않는다. 새 마이그레이션부터 작성 시점에 주석을 단다.

## 무엇을 설명하는가

각 선언과 의미 있는 코드 구간에 역할을 설명하는 주석을 반드시 붙인다. 이름이나 구현이 단순해도 생략하지 않고 짧게 작성한다. 복잡한 로직에는 처리 흐름과 그 순서가 필요한 이유를 추가한다.

- 호출자가 알아야 하는 입력 범위, `null`·빈 값·생략의 차이, 반환 순서, 단위, 공개 범위를 적는다.
- 트랜잭션 참여 조건, 잠금 순서, 실패 시 롤백 범위, 파일·스트림 해제 책임처럼 동작에 영향을 주는 조건을 적는다.
- 구현 내부에서는 특정 분기나 처리 순서를 유지해야 하는 이유를 해당 코드 가까이에 적는다.
- 단순한 선언은 짧은 역할 설명을 남긴다. 설명을 줄일 때도 선언의 주석 자체를 제거하지 않는다.
- 테스트를 작성하는 경우 테스트 메서드에도 검증 대상과 기대 결과를 짧게 적는다.

## 주석 필수 대상

직접 작성하는 코드의 다음 단위에는 빠짐없이 주석을 작성한다. 접근 제어자, 선언 길이, 이름의 명확성에 따른 예외를 두지 않는다.

| 대상 | 설명할 내용 |
| --- | --- |
| 클래스·인터페이스·record·enum·어노테이션 | 타입의 역할 |
| enum 항목 | 각 값의 의미 |
| 메서드 | 수행하는 작업과 필요한 호출 조건. 정적·인스턴스 메서드, `private`, `@Override`, 헬퍼 메서드도 포함 |
| 필드·상수 | 값의 역할. 엔티티·설정·의존성 필드도 포함 |
| record 구성요소 | 값의 역할. 타입 Javadoc의 `@param`으로 작성 |
| 생성자·초기화 블록 | 초기화 목적과 조건. 명시적인 생성자(record 압축 생성자 포함)는 각각 Javadoc 작성. Lombok이 생성한 생성자는 타입·필드 주석으로 설명. 초기화 블록은 바로 위에 일반 주석 작성 |
| 처리 구간·콜백·설정 구간 | 입력 검증, 조회, 변환, 저장, 응답 조립 등 해당 구간의 목적 |

Java 선언에는 여러 줄 Javadoc을 사용하고, 구현 내부의 처리 구간에는 `//`를 사용한다. 주석 문법이 없는 JSON 등의 파일에는 주석을 억지로 넣지 않고 관련 문서에 설명한다.

클래스 주석으로 내부 메서드·필드 설명을 대신하지 않는다. 구현 내부는 함께 수행되는 문장들을 의미 단위로 묶어 설명하며, 같은 목적의 모든 대입문마다 같은 설명을 반복하지 않는다.

## 문체와 정확성

- 설명은 한국어로 작성하고 코드 식별자, 표준명, 프로토콜명은 원래 표기를 사용한다.
- 요약·상세 설명·태그는 명사구 또는 `~함`, `~됨`, `~임`처럼 간결한 형태로 쓴다. `~한다.`, `~이다.`로 문장을 길게 풀어 쓰지 않는다.
- 문맥상 의미가 명확하면 `ID`, `제목`, `생성 시각`처럼 짧게 적는다. 짧은 설명 끝의 마침표는 생략한다.
- 간결하게 줄이더라도 입력 조건, 예외 조건, 자원 해제 책임처럼 필요한 정보는 남긴다.
- `기존처럼`, `이전과 동일`, `안전한`만으로 설명을 끝내지 않는다. 현재 어떤 조건과 동작을 보장하는지 적는다. 호환이 이유라면 유지하는 호환 조건(응답 키, 상태 코드, 메시지)을 명시한다.
- 보장 범위는 구현과 일치해야 한다. 예외 객체 생성, 예외 발생, HTTP 오류 응답 변환을 서로 구분한다.
- 비밀번호·토큰·개인 경로를 예제로 넣지 않는다. 주석 처리한 폐기 코드를 남기지 않는다.

## Javadoc 형식

Javadoc은 문서화할 선언과 그 어노테이션 바로 위에 둔다. 첫 문단에는 선언의 책임을 요약하고, 상세 설명과 태그는 빈 줄로 구분한다. `{@link Type#method()}`·`{@code value}`와 표준 태그를 사용한다.

### 선언 사이의 간격

- 앞선 선언·코드 구간과 다음 Javadoc 블록 사이에는 빈 줄 한 줄을 둔다. 의존성 필드, enum 항목, 메서드에도 같은 기준 적용.
- Javadoc의 닫는 ` */`와 해당 선언의 첫 어노테이션 또는 선언 사이에는 빈 줄을 넣지 않는다.
- 파일 첫 선언이나 여는 `{`, `(` 바로 뒤의 첫 주석 앞에는 구분용 빈 줄을 추가하지 않는다.

```java
/**
 * 주문 생성·상태 전이
 */
@Service
@RequiredArgsConstructor
public class OrderService {
    /**
     * 주문 저장소
     */
    private final OrderRepository orders;

    /**
     * 주문 상품 저장소
     */
    private final OrderItemRepository items;
}
```

### 여러 줄 작성

내용 길이나 태그 유무와 관계없이 항상 여러 줄로 작성한다. 한 줄 Javadoc(`/** ... */`)은 허용하지 않는다. 여는 `/**`와 닫는 ` */`는 각각 독립된 줄에 두고, 본문의 각 줄은 ` *`로 시작한다. `/**` 다음에 빈 줄을 넣지 않고, 요약 없이 태그만 작성하지 않는다.

```java
/**
 * 업로드 사진 바이트 조회
 *
 * 운영자가 아니면 공개 상품·게시글·공지 또는 본인 주문에 쓰인 사진만 허용
 *
 * @param key {@code post|product/<uuid>.<ext>} 형식의 저장 키
 * @param userId 세션 사용자 ID, 비로그인이면 빈 값
 * @return 파일 바이트
 * @throws ApiException 형식이 다르거나 접근할 수 없거나 파일이 없을 때(404)
 */
```

### record

record 구성요소는 타입 Javadoc의 `@param`으로 각각 설명한다. 구성요소가 많아도 생략하지 않는다.

```java
/**
 * 재고 조정 결과
 *
 * @param adjustment 저장한 조정 기록
 * @param stock 조정 후 재고
 */
public record AdjustmentResult(InventoryAdjustmentResponse adjustment, int stock) {}
```

## 엔티티 필드

엔티티의 각 필드에는 무엇을 나타내는 값인지 짧은 Javadoc을 붙인다. `id`, `name`처럼 이름이 명확한 필드도 생략하지 않는다. 접근 제어자와 상태 변경 방식은 [CODE.md](CODE.md#jpa-엔티티)를 따른다.

- PK, 일반 컬럼, FK 컬럼, `@Transient` 필드를 포함한다.
- Javadoc은 해당 필드의 첫 어노테이션 바로 위에 둔다. 어노테이션이 없으면 필드 선언 바로 위에 둔다.
- 짧은 명사구로 값의 역할을 설명하고, 해석에 필요한 경우에만 `null`의 의미, 단위, 호환 목적을 덧붙인다. 다른 대상을 참조하면 `주문 ID`, `상품 ID`처럼 구분한다.

```java
/**
 * 상품 ID
 */
@Column(nullable = false)
private UUID productId;
```

## 태그와 참조

태그는 시그니처에 드러나지 않는 계약을 보완할 때 사용한다. 모든 인자에 태그를 기계적으로 추가하거나 요약을 반복하지 않는다. 엔티티 필드의 짧은 설명에는 태그가 필요하지 않다.

`{@link Type#member}`·`@throws ExceptionType`의 타입은 [import 규칙](CODE.md#import와-타입-참조)에 따라 파일 상단의 import를 공유하고 단순 이름으로 작성한다.

| 문법 | 작성 기준 |
| --- | --- |
| `@param name` | 입력 범위, 단위, 생략·빈 값의 의미 등 추가 설명이 필요한 인자. record는 모든 구성요소 |
| `@return` | 반환값의 의미, 정렬, `null`·빈 결과. `void` 메서드에 사용하지 않음 |
| `@throws ExceptionType` | 호출자가 알아야 하는 예외 타입과 발생 조건. HTTP 상태는 괄호로 덧붙임 |
| `{@link Type#member}` | 실제로 참조할 수 있는 타입·메서드·필드 |
| `{@code literal}` | 경로, 설정 키, SQL 열, 리터럴 |

태그는 각각 새 줄에 두고 `@param` → `@return` → `@throws` 순서로 정리한다. `@param`은 선언의 인자 순서를 따른다. 항상 예외를 던지는 메서드는 반환 설명을 만들지 않는다. 예외 객체를 만들어 반환하는 메서드는 `@return`에 예외 객체라고 적는다.

## 복잡한 처리 흐름

여러 단계의 처리, 중첩 분기·반복, 트랜잭션·잠금, 외부 결제 연동, 재시도·실패 복구처럼 순서나 조건을 따라가야 하는 코드에는 흐름 설명을 반드시 추가한다.

- 선언의 Javadoc에는 요약 뒤에 주요 처리 순서를 번호 목록으로 적는다.
- 구현 내부의 각 처리 구간 바로 위에는 `//`로 그 단계의 목적을 적는다. 분기 기준, 조기 종료 조건도 필요한 위치에 설명한다.
- 순서가 중요하면 이유를 적는다. 잠금 취득 순서, JPA flush와 jOOQ 조회 순서, 실패 시 함께 롤백되는 범위를 명시한다.
- `1단계`, `처리 시작`처럼 내용 없는 구획 이름만 붙이지 않는다.

```java
/**
 * 주문 생성
 *
 * 하나의 트랜잭션에서 실행, 실패 시 주문·재고 차감·재고 이력이 함께 롤백됨
 *
 * 1. 옵션 행을 ID 순서로 잠금(동시 주문 교착 방지)
 * 2. 판매 여부·재고 확인 후 서버 가격으로 합계 계산
 * 3. 주문·주문 상품 스냅샷 저장, 재고 차감과 이력 기록
 */
```

## 일반 주석과 다른 언어

- Java·TypeScript·JavaScript의 처리 단계와 이유는 `//`로 작성한다. `/** ... */`를 구획 구분선이나 실행문 묶음의 제목으로 사용하지 않는다.
- TypeScript·JavaScript 선언 문서도 항상 여러 줄로 작성하되, 태그는 해당 언어의 문서 주석 문법(TSDoc)을 사용한다.
- 짧은 `/* ... */`는 빈 `catch`처럼 코드 내부에서 설명이 필요한 곳에 사용할 수 있다. 실패를 무시해도 되는 이유와 대체 동작을 적는다.
- CSS는 `/* ... */`, SQL은 `--`, YAML·Dockerfile·셸·환경 설정은 `#`으로 작성한다.
- `TODO`·`FIXME`가 필요하면 남은 작업, 이유, 해소 조건을 함께 적는다. 완료되면 제거한다.

## 변경 시 확인

- 동작·이름·책임이 바뀌면 관련 주석도 함께 갱신하거나 제거한다.
- 요약, 태그, 심볼 링크가 현재 선언과 일치하는지 확인한다.
- 추가·수정한 모든 선언과 처리 구간에 역할 설명이 있는지 확인한다. `private`·`@Override`·헬퍼도 빠뜨리지 않는다.
- 앞선 선언과 다음 문서 주석 사이에 빈 줄 한 줄이 있고, 문서 주석과 설명 대상은 붙어 있는지 확인한다.
- 복잡한 로직에는 Javadoc의 전체 흐름과 구현 내부의 단계·분기 설명이 모두 있는지 확인한다.
- 컨벤션 준수 여부와 코드 동작 검증을 구분한다. 주석 형식 확인만으로 동작을 검증했다고 보고하지 않는다.
